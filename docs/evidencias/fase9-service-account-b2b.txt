Fase 9 — Service Account B2B (partners-integracion -> E14)

Cliente: partners-integracion   (realm agencias-partners)
  - clientAuthenticatorType: client-secret
  - serviceAccountsEnabled: true
  - standardFlowEnabled: false
  - directAccessGrantsEnabled: false
  - audiences: incluye turismo-api (mapper hardcoded)
  - roles de cliente: disponibilidad.consultar

Flujo B2B (no hay usuario humano, solo maquina a maquina):

  1) partners-integracion pide token con grant_type=client_credentials:
     POST http://localhost:8080/realms/agencias-partners/protocol/openid-connect/token
     body: client_id=partners-integracion
           client_secret=***
           grant_type=client_credentials

     Respuesta: access_token con aud=turismo-api y
                resource_access.partners-integracion.roles=[disponibilidad.consultar]

  2) Backend recibe la llamada a E14 y la autoriza por:
     - multi-issuer resolver: issuer http://localhost:8080/realms/agencias-partners
       es uno de los issuers aceptados por SecurityConfig.
     - validador de audience: 'turismo-api' presente en aud -> OK.
     - regla declarativa en application.yml para /api/partners/**:
       requiere ROLE_disponibilidad.consultar -> OK.

  3) Prueba real (ver log de este archivo):
     GET /api/partners/disponibilidad?tourId=1&fecha=2026-12-01
     Authorization: Bearer <token de client_credentials>
     -> HTTP 200

este feature ya se implemento en F4 (multi-issuer) y F5 (reglas de ruta),
aqui solo se documenta y se verifica.
